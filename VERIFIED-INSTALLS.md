# Verified installs

**Marks.** ✅ verified - we ran it and read the answer. ◐ same core as the CLI - the CLI was verified, this
wrapper was not exercised. 📄 documented - a convention, nothing claimed.

**One core, one test.** Where a product ships a CLI and a GUI or IDE, the core is tested once and the
wrapper is marked ◐: they read the same config, the same plugin registry, the same hooks (CodeBuddy Code and
WorkBuddy share one CLI; a desktop app and its bundled CLI share one plugin registry; the Hermes app and its
CLI share `config.yaml`). CLI evidence does not transfer for **browser and OAuth hops**, for **session-end
behaviour** (only a real session ends), or where a GUI ships **its own snapshot** of the core.

Every row below was run against a real client on this machine, and each one says what it answered.

| Client | Command | What happened |
| --- | --- | --- |
| **Claude Code** 2.1.280 | `claude plugin marketplace add zeyu-j/centricmem-skill`, then `claude plugin install centricmem-skill@centricmem` | Both succeed and `claude plugin list` shows the plugin enabled. `claude plugin details` reports `Hooks (1) SessionStart (harness-only - no model context cost)`. On this machine the Claude binary itself would not start (the native build rejects this Windows), so the plugin tree is what was verified and no session was run |
| **Codex** 0.156.1 | `codex plugin marketplace add https://github.com/zeyu-j/centricmem-skill`, then `codex plugin add centricmem-skill@centricmem` | The marketplace is accepted and the plugin is cached at `~/.codex/plugins/cache/centricmem/centricmem-skill/<version>`. **Run `codex plugin marketplace upgrade` after a release**: Codex keeps the marketplace snapshot, so an install left alone kept serving 1.0.9 after 1.0.11 was published. Once refreshed, its installer copies `hooks/hooks.json` (SessionStart and SessionEnd) into the plugin cache, which is where Codex reads hooks from |
| **CodeBuddy Code / WorkBuddy** 5.6.2 | `codebuddy plugin marketplace add zeyu-j/centricmem-skill`, then `codebuddy plugin install centricmem-skill@centricmem` | Both succeed and `codebuddy plugin list` reports it enabled. The vendor's own validator agrees: `codebuddy plugin validate .` prints `Validation passed` for `.codebuddy-plugin/marketplace.json`, and its error text lists the manifest paths it accepts (`.codebuddy-plugin/`, `.workbuddy-plugin/`, `.claude-plugin/`). `codebuddy mcp list` shows the server too, awaiting a user approval rather than failing |
| **ZCode** 0.16.9 | `zcode plugins marketplace add zeyu-j/centricmem-skill`, then `zcode plugins install centricmem-skill@centricmem` | Marketplace added as `centricmem (1 plugins)`, plugin installed and `[enabled]`. ZCode preloads the Claude Code marketplace, so this package needs no ZCode-specific manifest. `zcode skills list` then shows `centricmem-agent` **twice** - the hub copy and the plugin copy - which is the duplicate-source case `cm_doctor` reports |
| **goose** 1.51.0 | `goose plugin install https://github.com/zeyu-j/centricmem-skill` | Reports `Installed open-plugins plugin` and imports `centricmem-skill:centricmem-agent`. No host-specific manifest folder is involved: goose reads the manifest at the repository root |
| **Hermes** v0.21.4 | `hermes skills install zeyu-j/centricmem-skill/skills/centricmem-agent --yes` | Fetches the tag, scans it (verdict SAFE) and lands `%LOCALAPPDATA%\hermes\skills\centricmem-agent` with `SKILL.md` byte-identical to the package; `hermes skills list` then reports `1 hub-installed`. `--yes` matters: without a TTY the confirmation prompt is auto-declined and the install is cancelled. Hooks live in `hermes/` and must be allowlisted before they fire |
| **OpenClaw** 2026.6.35 | `openclaw plugins install centricmem-skill --marketplace zeyu-j/centricmem-skill` | Installed as a **bundle** (it consumes the Claude marketplace format) and shown enabled. The `--marketplace` form is the one that works: a bare `openclaw plugins install git:...` is rejected with *missing `openclaw.extensions`*, because that route installs a code plugin and this repository ships none. `openclaw skills install ./skills/centricmem-agent --global` works from a clone |
| **Qwen Code** 0.24.4 | `qwen mcp add centricmem https://mem.centricmem.com/mcp` | Added to user settings as HTTP, and `qwen mcp list` shows it awaiting authorisation (`Disconnected`). Its extension and hook surfaces are in [`qwen/`](./qwen/) - a `qwen-extension.json` plus a `SessionStart` hook in its own JSON envelope, which the smoke job exercises on Linux and macOS |
| **Cline** 3.0.64 | `cline skill add zeyu-j/centricmem-skill` | Forwarded to the open skills CLI, so the Skill install is the same one-liner as everywhere else. `cline mcp list` needs a TTY and points at `cline config mcp` |
| **pi** 0.87.1 | `pi install https://github.com/zeyu-j/centricmem-skill` | The clone lands in `~/.pi/agent/git/github.com/zeyu-j/centricmem-skill` and `pi list` reports it under user packages. Installed from `@earendil-works/pi-coding-agent`; the unscoped `pi` on npm is unrelated. It has **no lifecycle hook surface** - its extension model is package resources toggled with `pi config`, and the Skill arrives through exactly that path |
| **Kiro CLI** | `kiro-cli mcp add --name centricmem --url https://mem.centricmem.com/mcp --scope default` | Answers `Added MCP server 'centricmem' to default config in ~/.kiro/settings/mcp.json`, and `kiro-cli mcp list` shows it under the default agent. This client takes flags only, so name and url cannot be positional, and its help contains no hook, plugin, marketplace or extension surface at all. The Kiro IDE is a separate program sharing the config directory, and its `.kiro/plugins/marketplace.json` is for the IDE, not this CLI |
| **nanobot** 0.3.5 | `cp -r skills/centricmem-agent ~/.nanobot/workspace/skills/` | `nanobot/agent/skills.py` reads one folder per Skill from `<workspace>/skills`, and the copy is in place alongside the user's own skills. `nanobot/agent/plugins.py` scans `<workspace>/plugins/*`, validates each package's `mcp.json` against the Agent Plugins schema this repository ships, and takes the `skills/` directory inside the package - so the whole bundle is accepted there too. Documented, not exercised in a live run |
| **Devin CLI** 3000.11.1 | `devin mcp`, `devin skills`, `devin plugins`, `devin doctor` | The surfaces exist and are listed at the top of [`devin/README.md`](./devin/README.md). Its plugin and skill pages need a browser to render, so no manifest is claimed; `devin plugin add .` also did not accept a local path when it was tried |
| **kilo** 7.7.9 | `kilo mcp add` | An interactive wizard, so nothing can be written non-interactively here; `kilo mcp list` reports no servers. Its plugins are npm modules, so a marketplace entry would mean publishing a package - not done |
| **junie** | `junie --mcp-default-locations` / `--mcp-location` | MCP locations are flags and `~/.junie/` holds only logs, so this host is documented rather than wired |
| Cursor, Grok and the private clients whose manifests are not published here | per-host manifests in this repository | **Install not verified here for the GUI-only ones**: those manifests follow the published convention and nothing more is claimed. A private desktop coding agent of ours was exercised through its own package tool instead, and is left unnamed on purpose: its tree was still carrying a 0.21.90 copy of this plugin, and `plugin install <repo> --replace --yes` refreshed it and reported `mappedCapabilities: [skills, hooks], hookCount: 2`, so it runs the shared `hooks/hooks.json`. Its MCP connection was a separate step, as it is everywhere |

If one of the unverified rows is wrong, the fix is a manifest change rather than a code change: open an issue
with the client's version and what its installer said.
